Why this is happening
The Meta business verification and Meta payment-card approval are two separate checks.

AutoGamma’s business can be fully verified, but Meta can still reject the payment card because of:

Bank or country restrictions
International or recurring payments disabled
3-D Secure/payment authentication failure
Prepaid, virtual, or unsupported card type
Billing address or business details not matching
Existing unpaid Meta balance
Payment account or Business Manager restriction
Currency or billing-country mismatch
Meta requiring a payment method for WhatsApp Business messaging limits
Airavata cannot bypass this card validation because it happens inside Meta’s own Embedded Signup and billing system. If Meta rejects the card, the signup usually never reaches the successful FINISH stage, so Airavata does not receive the WABA and phone-number details.

What the code does after Meta accepts the card
The current flow is already designed for the AutoGamma setup:

AutoGamma logs into their Airavata account.
They click Connect Facebook / Embedded Signup.
Meta handles:
Business selection
WABA creation or selection
Phone-number selection
Payment setup
Permissions
Meta sends Airavata an authorization code.
Airavata exchanges that code with Meta.
Airavata receives:
WABA ID
Phone Number ID
WhatsApp access token
The access token is encrypted and stored against AutoGamma’s user account.
The account is marked connected only after the encrypted credentials are successfully saved.
The stored connection is tenant-specific. AutoGamma’s credentials are not mixed with another client’s credentials.

Will messages be sent from AutoGamma’s WhatsApp business account?
Yes.

For ordinary client accounts, message sending uses the encrypted WhatsApp credentials stored for that specific user. The message is sent through that client’s:

WABA
Phone Number ID
Meta access token
The webhook also identifies the owning user from the Meta phone number ID, so incoming messages and delivery updates are associated with the correct client workspace.

Will the credits assigned by the Admin be used?
Yes, for Airavata’s internal credit system.

When Master Admin gives AutoGamma credits:

AutoGamma’s creditBalance increases.
A credit transaction is recorded.
Template messages check the available balance before sending.
Credits are reserved before Meta is called.
If Meta rejects the message, the credits are refunded.
If the send succeeds, a deduction transaction is recorded.
The current credit rules are:

Marketing templates use the Marketing rate.
Utility templates use the Utility rate.
Authentication templates use the Authentication rate.
Normal free-form WhatsApp session messages are not charged Airavata credits.
Important distinction
Airavata credits and Meta billing are separate systems.

Admin-assigned Airavata credits control usage inside this platform. They do not replace Meta’s requirement for an accepted payment method.

So AutoGamma may need:

An accepted Meta payment method for the WhatsApp Business account.
Airavata credits assigned by your Master Admin.
The Meta card is needed for Meta’s own billing and account activation rules. The Airavata credits are used for your platform’s message-credit rules.

How to confirm where the failure occurs
After AutoGamma retries, these are the expected checkpoints:

The Embedded Signup window must reach Meta’s successful completion step.
Browser logs should show the Embedded Signup FINISH event.
The API should log that Meta’s authorization code exchange succeeded.
The API should log that encrypted WhatsApp credentials were stored.
AutoGamma’s user record should show:
Connected status
WABA ID
Phone Number ID
A test message should use AutoGamma’s phone number, not the ecosystem/admin number.
If Meta rejects the card before the FINISH event, the problem is entirely on Meta’s billing/payment side and no WABA credentials will be stored yet.
